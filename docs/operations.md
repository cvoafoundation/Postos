# CVOA.ONE Operations

Operations is a native `/operations` tab using the existing CVOA identity. It implements scoped channels, participant-only one-to-one direct messages, threaded messages, mentions, reactions, pins, message search, private attachments, channel read markers, active-member/typing indicators, and in-memory drafts. National can oversee organizational channels; state commanders can manage their assigned state and its posts; post leadership manages its own posts. Verified members can participate in channels available to their affiliation. Staff-only and restricted channels narrow readership. Direct messages exclude organizational oversight. Tribunal records remain in their existing separate system.

The Actions view records one owner, an outcome, measure, deadline, status, and optional 90-day cycle. Messages can create actions. Activity capture records engagements, intelligence, opportunities, and atomic assigned follow-ups. Monthly reports capture Completed, Next, and Blocked. Workspace overview aggregates authorized organizational channels and excludes direct conversations. The SOP tab is an 18-section working summary of SOP-001, not an adopted policy; effective date and approval authority remain to be recorded.

All Operations tables have RLS. Backend predicates use existing authoritative profile/appointment scopes, suspension and deletion state, never editable JWT metadata. An owner must already have channel access before receiving an action. Message attachments inherit channel read access and use short-lived signed URLs. Uploaded files are private, limited to 10 MB each, and restricted to supported document/image types. Client hard deletion of attachments and records is disabled. Edits, moderation, task updates, and report updates preserve protected history. Only authors edit message text; organizational leadership may remove messages without impersonating their author. Archived channels stop new activity.

Realtime messages and new reactions use RLS-protected Postgres Changes. Presence uses database heartbeats, with an active indicator for the selected channel within the last 90 seconds. Visible screens refresh every 30 seconds as a reconnect fallback; reaction removal may wait for that refresh. Drafts stay in account-scoped memory and clear on account/workspace change. Channel and thread queries discard stale responses. Search and message history are paginated/bounded. This release does not include voice/video calls, external Slack import, push/email notifications, advanced rich-text editing, or multi-person direct chats.

Release: apply `20261013220149_operations_workspace.sql`, then deploy the frontend. No new external accounts, environment variables, or sending credentials are needed. State/post default channels are provisioned lazily for accessible workspaces. National announcement, general, and National staff channels are seeded.

Validation: `node --test tests/operations.test.mjs tests/operations-ui.test.mjs` exercises database boundaries, threads, mentions, file ownership, direct-message isolation, moderation/history, accountable owners, atomic follow-ups, reporting, suspension, and the interactive interface. `npm run build` verifies the production frontend. Database tests run inside PGlite; live permission smoke tests should use a transaction and roll back fixture records.

## Action-first navigation

Operations opens on Home, with a short getting-started walkthrough, personal action counts, assigned/overdue/blocked work, authorized team conversations, and recent reports. The compact navigation rail offers Home, My work, Conversations, Mentions, Overview, and Guide. Guide explains the workflow before the SOP summary. My work filters by the signed-in user in the database query. Home reads existing RLS-protected records, refreshes every 30 seconds, and displays bounded results (200 earliest actions, 20 reports). No permission or schema changes accompany this layout.

## Connected modules and assistant

Home now loads `ops_module_queue`, which reads the existing staff action queue (meetings, minutes, membership, applications, launch reviews/tasks, fundraising, transfers, and escalations) and RLS-protected sponsorship follow-ups. Members receive accessible upcoming URO sessions and their own URO actions without obtaining staff privileges. Sponsor follow-up is flagged after seven days without a sponsor record update; meetings and agreement renewals use a 30-day horizon. No duplicate work records are created. The original module owns status and completion; Operations refreshes every 30 seconds and on window focus. Source dates are shown as reference/due dates because some review records use their submission date rather than a formal deadline.

The Assistant rail item invokes `cvoa-assistant` under the signed-in user's JWT. The Edge Function validates the user and uses a public client with that JWT so RLS applies to every context query. It reads up to 40 connected items and 20 personal open Operations actions. Selecting a team adds up to 10 reports and 15 engagement summaries. Direct messages, Ethics Tribunal tables, member records, and health modules are not queried. Each question retrieves fresh context; prior prompts and answers are not sent as history or stored by the application. Answers are drafts and guidance, with source buttons constructed from authorized records. The assistant has no write tools.

Deployment: apply `20261013230000_operations_module_connections.sql`, deploy `cvoa-assistant` with JWT verification enabled, then deploy the frontend. Reuses the server-side `ANTHROPIC_API_KEY` already used by CVOA document generation. Optional `CVOA_ASSISTANT_MODEL` overrides the default `claude-sonnet-4-6`. Missing provider configuration returns an explicit unavailable message. Never put either API credentials or service-role credentials in the browser. This function does not use a service-role client.

`ops_ai_reserve` keeps usage counters only in the unexposed `operations_private` schema, allows five requests/minute and fifty/day per active member, and serializes concurrent reservations with a row lock. Failed provider requests count toward the limit. The assistant currently uses Anthropic's API, so provider billing and data handling apply. Tests cover RLS source isolation, member/staff differences, source lifecycle, per-user limits, suspended access, invalid input, private-message exclusion, endpoint authentication/configuration, and UI source links.

The private usage counter deliberately has no user grants or policies (default deny). The authenticated `ops_ai_reserve` SECURITY DEFINER RPC is intentional: it only reserves a request for `auth.uid()`, checks active membership, and returns a boolean. It exposes no counters, records, or caller-selectable identity. The readiness GET endpoint returns only whether the provider key exists, with deployment JWT verification enabled; it performs no model call and returns no secret.

## Temporary National-only rollout

Operations, connected module work, and the assistant are currently restricted to active National Commander or National staff appointments. The sidebar and direct route enforce this gate, and the private Operations eligibility helper closes existing channels, tables, realtime delivery, and attachments to non-National accounts. The module queue and assistant also check the gate. Records and original module permissions are preserved for a future expanded rollout. API-key setup remains required for AI generation.
